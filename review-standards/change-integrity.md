# change-integrity

改動有沒有把舊行為、成對的另一邊、宣稱的效果與看不到的外部前提一起顧到。手法取自 Walden Yan 公開的 `/walden-review` skill（2026-10-21，sweep J／B／D／K 與原則 19），只吸現有標準沒有的部分；重用與複製貼上沿用 `pr-review-baseline-reuse`、`pr-review-baseline-quality`，沒 caller 的假抽象沿用 `pr-review-baseline-design-decay` 第 7 項，單位與時區漂移沿用 `design-and-maintainability`，不在這裡重報。

## 適用

角色：code-reviewer、typescript-reviewer、python-reviewer。任何語言、任何 repo。各段有自己的觸發條件，沒觸發的段在「這次審查範圍」歸到「相關但沒套用」並寫一句原因。

## 1. 舊行為清點（刪除或替換有邏輯的舊程式時）

觸發：diff 刪除或替換帶條件分支、副作用、錯誤處理、權限、快取、鎖、重試或排序的舊程式。純改名、搬位置但內容不變、只刪 import 或註解，不觸發。

1. 把舊程式當規格讀，在比較範圍起點（base）上列出它保證的每一件事，單位寫成「在什麼條件與範圍內，保證什麼行為」。只寫「有權限檢查」不夠；要寫「寫入前先驗呼叫者對該租戶有寫入權」。
2. 對每一條，在新程式找接手處並附 `path:line`。
3. 分三類：保留（同條件、同順序、同範圍）、找不到接手處、找得到但保證變了（順序對調、範圍變寬或變窄、只剩部分路徑做得到）。
4. 後兩類各寫成 finding，形狀是「舊程式在 X 條件下保證 Y，新路徑在哪裡做？」。這類 finding 定嚴重度前會過 `bitbucket-pr-review` 的 6c（設計意圖、耦合殘留還是真防護、新契約下誰接手），所以這裡只負責找出來，不自己判是不是刻意的。
5. 清點表完整放在你的審查輸出裡（它會進完整證據副檔）；保留類不寫成 finding。觸發了卻沒交清點表，在「這次審查範圍」把本段記為沒完成並寫原因。

## 2. 新舊並存與沒接上的東西

knip 這類工具抓得到「沒人 import 的 export、檔案、依賴」，抓不到下面兩種。兩種都先當搜尋候選，查完才成為 finding：

- **新舊並存**：新程式取代了某個舊實作（同一件事的新版本），但舊實作仍有呼叫端。先確認是不是刻意保留的相容路徑（PR 描述、spec、註解有沒有寫、舊呼叫端是不是外部契約）；不是刻意的，才問「舊的那份和它的呼叫端什麼時候遷？」。
- **宣稱要生效卻沒接上**：新參數沒有任何呼叫端傳值、新欄位寫了沒人讀、新設定 key 沒人消費、新 enum 成員沒人產生。報之前排除合理預設值、框架或序列化讀取、字串鍵登錄表、另一個 repo 或前端消費。查不完消費邊界（例如可能被另一個 repo 讀）就不報成缺陷，改走第 5 段。

分級：屬於「做了不必要的擴充」的沿用維護性標準的分級；屬於「功能宣稱會生效但實際沒接上」的，照行為缺陷分級。

repo 沒有 knip 或同類工具時（看 `package.json` scripts、CI 設定、pre-push hook），才另外檢查 diff 新增的 export 有沒有 importer；有工具的 repo 跳過，不重做機器已經做的事。

## 3. 成對的面與跨服務契約

- **成對的面**：改到環境設定、同一後端的某個 client、同一功能的某個畫面時，先確認另一邊和它之間有沒有必須一致的共同契約。有共同契約才追另一邊，結果分四種：已同步、本來就不需要同步、PR 明講延後、未知。前三種不報；確認不一致而且違反契約的照常成為 finding；未知的走第 5 段。
- **跨服務契約**：程式碼碰到另一個服務的介面（前端呼叫後端、client 呼叫 API、服務呼叫外部系統）時，要對到對方實際收什麼、回什麼，不拿「型別檢查過了」當成對了。具體地雷記在各 repo 的 `CLAUDE.md` 或規則檔，照 `project-conventions` 讀進來對照。

## 4. 宣稱與回歸測試

- **PR 描述與 commit 的行為宣稱**：「修好 X」「變快」「相容舊版」「處理了所有邊界情況」這類具體宣稱，要有程式碼、測試或 log 實際涵蓋那一項；證據只涵蓋一部分時，報告只承認被涵蓋的範圍。空泛形容詞不管。最高 Should Fix（文件說法不符不擋 release，見 `bitbucket-pr-review` 6d）。
- **修 bug 的回歸測試**：PR 標題或 commit 以 `fix` 開頭，或描述說修了某個 bug 時，要有一個在修正前會失敗的測試，而且它要碰到原 bug 的觸發情境與失敗邊界；只驗 mock 假設或測另一條路徑的不算。沒有就報，最高 Should Fix。
- 同一個證據缺口同時命中這兩條或既有的 Missing tests 時，合併成一筆。

## 5. 答案在程式碼之外的事

判斷要靠程式碼以外的資訊時（正式環境的資料量或設定、部署方式、產品意圖、作者能不能實際測到這條路徑）：

1. 先查能回答這一題的權威來源：這個 PR 的 spec 或票、repo 內文件、團隊知識庫（例如 `acme-product-knowledge`）、對方服務的程式碼。查到足以回答就停，不把來源清單逐項走完；來源讀不到、或不能代表目標環境（例如後端最新程式不代表正式環境部署的版本）時，寫明限制。
2. 查到答案：照答案判斷，有問題就是一般 finding，沒問題就不報。
3. 查不到，而且同時滿足下面三點，才輸出一個 `OPEN_QUESTION` 區塊，不寫成 finding、不給嚴重度：
   - 已確認的改動或執行路徑讓這題與本 PR 相關（附 `path:line`）；
   - 除了這一項未知，其他前提都已查證；
   - 萬一答案是壞的，後果會到 Must Fix 等級（不修就壞會出貨的東西）。

   ```text
   OPEN_QUESTION:
   question: <一句問句，不下斷言>
   relevance: <哪個已確認的改動或路徑讓它相關，path:line>
   unknown: <剩下哪一項前提查不到>
   checked: <查過哪些來源、各自為什麼答不了>
   impact: <答案是好或壞時，處置分別怎麼變>
   ```

4. 不符合上面三點的未知不報。不用問句代替查證，也不把同一個未知換句話問兩次。
