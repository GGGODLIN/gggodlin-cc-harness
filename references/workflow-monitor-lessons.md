## Watch plumbing

- **watch must be main-session-launched** — only a `Bash(run_in_background=true)` watch gets the "exit → wake the session" bridge. The hook can only *ask* the session to start it; it can't start one with the bridge itself.
- **`TaskStop` is the reliable way to stop a watch — shell `kill` is now the fallback** (2026-08-01, supersedes the TERM→KILL escalation below as the *primary* path). Live case: a watch armed for a daily-topic-analysis run (zsh wrapper PID 6031 + bash child 6114) survived `kill` **and** `kill -9` — the cleanup block printed its loud `❌ STILL ALIVE`, exactly as designed. `TaskStop({task_id: "b7s9gwtez"})` then dropped it on the first call, `pgrep` went empty immediately, and the same thing worked again later that session on a second watch (`bbclv9lv7`). That asymmetry is side evidence for the job-control hypothesis below — CC's `run_in_background` job control holds these processes, so only the harness's own stop path reaches them; signalling the PIDs directly is fighting the wrong layer. Consequence baked into the steps: all three cleanup blocks are TaskStop-first with the shell chain demoted to fallback, and Step W.5 / Step 2.7 back-fill `watchTaskId` into the state file because `TaskStop` needs that id and it cannot be recovered after the launch result scrolls away. If you ever find yourself escalating to `kill -9` on a watch, the real problem is a missing `watchTaskId`. **And a missing one is gone for good — there is no programmatic recovery** (verified 2026-08-01): `TaskList` is the todo-task system (the `TaskCreate`/`TaskUpdate` family), and it lists neither background bash tasks nor workflow tasks — querying it for the id returns a bare `No tasks found` even in a session that just ran both. So once the launch result scrolls away, that watch's only remaining path is "try the shell kill, and if it fails hand the orphan to the user as a manual cleanup". That irreversible one-shot window is the entire reason the back-fill is its own numbered step instead of a parenthetical reminder.
- **Kill silently fails (root cause unknown) — must always verify post-kill** (added 2026-06-19 after the `awk→cut` patch landed but cleanup still left zombies). After patching `awk '{print $1}'` → `cut -d' ' -f1` the cleanup chain LOOKED correct in isolation testing (proven on a `sleep 60` test process), but on the real workflow watcher the next live run STILL reported `watch cleaned` while `pgrep` showed both the zsh wrapper + bash child surviving 1+ hour. Forensics couldn't pin the cause — the bash output file confirmed cleanup ran, the chain works on isolated processes, the watcher script has no respawn logic (80-line `while true; sleep $POLL; done`). Hypotheses (all unverified): CC harness's `run_in_background` job control might re-attach the process; `xargs -r kill` might receive an empty PID list under some timing race; the watcher's zsh wrapper's `eval` might capture+restart the bash child via shell job control. Fix: regardless of root cause, **every fallback cleanup block must run TERM → sleep 0.5 → re-pgrep → escalate to KILL → sleep 0.3 → re-pgrep → loud `❌` if still alive**. The verification step is non-negotiable — never trust `kill` to silently succeed in CC's background-task context.
- **CC harness rewrites `$1` inside skill markdown to the active workflow's task id — never use `awk '{print $1}'` here** (added 2026-06-19 after a second live misfire the same day). Symptom: every cleanup run the user sees `watch cleaned` but `pgrep -lf <watcher>` still lists the watcher; over multiple workflow turns the watchers accumulate as orphans. Root cause: when the Skill tool injects this markdown into the LLM's context, some hook/template pass scans the body for `$1` and substitutes the active background task's id verbatim — so the LLM sees `awk '{print task=<taskid>}'`, which awk evaluates as an empty variable assignment, prints nothing, and `xargs -r kill` silently no-ops. The original source on disk is correct (`awk '{print $1}'`); the rewrite happens **at injection time, not in the file**. Verified by inspecting the rendered Skill output for run `wf_8550cb5b-3be` vs `grep -n 'awk' workflow-monitor.md`. Fix: use `cut -d' ' -f1` instead — it has no `$` and survives the rewrite, equivalent semantics (first whitespace-delimited field). Same restriction applies to any future shell snippet in the command: avoid `$1`, `$2`, `$NF` etc. inside single-quoted awk format strings. Cleanup of accumulated orphans: `pgrep -f workflow-limit-watch.sh | while read pid; do kill -9 "$pid"; done` (the `while read` form doesn't go through awk at all).
- **`pgrep -lf` output can span MULTIPLE lines per process — `cut -d' ' -f1` then picks up non-PID tokens** (added 2026-07-17 live incident; likely the true root cause of the "root cause unknown" entry above). The zsh wrapper's command string contains literal newlines (`export ...` / `: && setopt ...` / `eval 'bash ...'` on separate lines), and `pgrep -lf` prints them raw — so one watcher appears as several output lines, and `grep -F "$SESSION_ID"` matches both the PID-bearing first line AND continuation lines like `eval 'bash ~/.claude/scripts/workflow-limit-watch.sh ... "<sid>" ...'` whose first field is `eval`, not a PID. The pids variable then carries garbage tokens; kill chokes on them and the cleanup chain mis-reports while real PIDs were never cleanly signalled. Fix (applied to all fallback cleanup blocks 2026-07-17): every `cut -d' ' -f1` is followed by `| grep -E '^[0-9]+$'` so only numeric tokens survive. Verified live 2026-07-17: pre-fix cleanup reported ❌ still-alive twice; `kill -9` on the two real PIDs directly succeeded immediately.
- **Per-session isolation — never `pkill -f <watcher>`** (added 2026-06-19 after a live misfire). The OG skill used global pgrep/pkill on the assumption "one CC session per box". False on a workstation with multiple sessions: a global `pgrep` matches another session's watch and silently skips arming yours (your workflow runs unprotected); a global `pkill -f` collaterally kills another session's watch (it happened — daily-topic-analysis cleanup killed a devspace-pr-review-eval session's watch, leaving its workflow unguarded). Fix: tag each watch with `SESSION_ID` in argv (5th arg to every watcher script), then `pgrep -af ... | grep -F "$SESSION_ID"` for detection and PID-filtered kill for cleanup. State files and args sidecars are also per-session. Verified 2026-06-19: two watches with different `SESSION_ID` args coexist on the same box; each tagged with its session id in `ps`, PPID chains diverge so each watch's exit wakes only its spawning session.
- **Always arm watch — no judgement** (user standing instruction 2026-06-06). Arm on every background workflow launch; never skip because a run "looks short". Arming ≈ free (one idle poll); not arming risks an asymmetric loss (blown quota window + re-spent tokens).
- **task_id**: watch mode captures it at launch into the state file → pause reads it there. Without watch, it only comes from the launch result in context (TaskList never lists workflow tasks; a running workflow has no journal yet).

## Cache and resume semantics

- **Cache boundary = agents journaled, NOT progress shown** — an agent whose side-effect ran but wasn't journaled before the kill RE-RUNS on resume. Harmless for side-effect-free agents (deep-research search/fetch/verify recompute); for agents with EXTERNAL side-effects (file writes, API calls, messages) that one re-run repeats the side-effect — make them idempotent.
- **Cache replay needs DETERMINISTIC prompts, or resume re-runs almost everything** (the load-bearing caveat, measured 2026-06-07). Resume re-executes the script body top-to-bottom and only cache-hits agents whose prompt reproduces byte-identical. A workflow that computes agent prompts from nondeterministic intermediate state (mutable counters, no-barrier `pipeline()`/`parallel()` completion-order races, unsorted dedup) diverges at the first such agent and re-runs it + all downstream. Real case: deep-research-paced paused at 83/100 agents replayed only **6** (the deterministic Scope+Search prefix) and re-ran 94 — its original Fetch phase picked URLs via a no-barrier pipeline + mutable `fetchSlots`, so fetch prompts (and the claims/verify prompts derived from them) differed every run. Fix was to make Fetch deterministic (barrier-collect search → fixed-order URL selection). **Before trusting "resume is cheap" for any workflow, confirm its agent prompts are deterministic from the journaled prefix; if not, pause→resume ≈ full re-run and you should instead switch to a fresh account and let it run to completion.** The earlier "stop at 3/6 → re-spent ~half" figure was a toy sequential workflow; do NOT assume real phase-structured workflows resume cheaply unless they were built deterministic.
- **Audit "did resume actually replay?" by counting fresh `agent-*.jsonl` per launch window vs journal `agentCount` delta — NOT by utilization %** (the deterministic fix CONFIRMED working end-to-end, 2026-06-07 F10). A 3-window resume (owner→alex→alex) of the post-fix deep-research-paced produced fresh agent jsonls of **52 / 60 / 11** while journal `agentCount` went **52 → 106 → 110**. Read it: window 2 spawned 60 fresh but journal only +54 → it replayed the prior 52 (Scope/Search/Fetch — the HEAVY phases, fetch of 27 full sources) and only re-ran +6 in-flight verify; window 3 spawned 11 but journal +4 → +7 in-flight verify re-run. **If it had integrally re-run (the pre-fix disaster), window 2 would show ~106 fresh jsonls, not 60.** Audit command: `find <transcriptDir>/wf_<id> -name 'agent-*.jsonl'` bucketed by mtime per launch window, compared to journal `agentCount` increments — the gap (here 13 of 123 total) is the in-flight batch boundary (pause lands mid verify-batch; those 2-claim×3-vote agents weren't journaled yet so they re-run). That gap is normal, small, and ALWAYS the light phase (verify), because pause lands in verify while the heavy phases already replayed. **Never infer re-run from utilization %** — Team(5x) vs Max(20x) are not comparable and util isn't linear in tokens (that was the F15 mis-inference, corrected only after counting jsonls). Token reality of that run: 123 fresh agents, 63M raw throughput (60% cheap cache_read), 265K output — the bulk is the topic's fixed cost (6 angles / 27 sources / 75 verify), not resume overhead; one-window-on-Max would only save the ~13 boundary re-runs.
- **Cache is hash-named jsonl files on disk, NOT inside the journal** (discovered 2026-06-14 F8 rescue). `subagents/workflows/wf_<runId>/agent-<hash>.jsonl` files are the actual cache — filename hash = (prompt, opts) hash, file content = full agent transcript with final StructuredOutput tool_use input. The journal `.json` is a metadata index (agentCount / status / args / etc.); journal corruption does NOT destroy cache, jsonl files survive. This is why **manual aggregation rescue** works: even after a bad resume overwrites journal `.args` to nonsense, the jsonl content is intact — read it with python, classify by phase prompt prefix, extract StructuredOutput, tally votes, write the report yourself. See `[[reference_workflow_jsonl_cache_rescue_pattern]]` for the template.
- **Same-session only** — the journal persists on disk but `resumeFromRunId` only works in the originating session. Keep CC OPEN during the pause.

## Args and GOLDEN

- **DO NOT re-pass args via the Workflow tool args parameter — main session LLM cannot achieve byte-identical args reproduction** (verified 2026-06-14 F8 case, failed twice trying). Unicode normalization happens at the cognitive layer: full-width「：（）；，」get unconsciously rewritten to half-width, markdown bold sometimes dropped. Even staring at the raw sidecar trying to "copy exactly", the LLM token-generation layer normalizes the output. There is no main-session workaround — the only fix is the **inject-and-resume helper** (Step 3.4), which bypasses the LLM entirely via `bash`+`python` byte-faithful file IO writing the args into the script literal. The Workflow tool call then carries only ASCII parameters (`scriptPath`, `resumeFromRunId`), no args, no normalization risk.
- **Resume re-runs the script body from the top — so the original `args` MUST be re-passed, byte-identical.** The journal caches `agent()` *results*, but the script statements above the first `agent()` (arg parsing, the `if (!QUESTION) return` guard in deep-research, etc.) execute fresh every resume. Omit `args` and an arg-reading script bails at its guard → that failed run "completes" with `agentCount=0` and **overwrites the journal, destroying the cache prefix**.
- **GOLDEN snapshot is the load-bearing safety mechanism — make it FIRST after pause, before ANY resume attempt** (Step 2.5). Without GOLDEN, a single bad resume permanently pollutes journal+jsonl and you lose retry capability. WITH GOLDEN, "fork-from-GOLDEN" lets you infinitely restore-and-retry — GOLDEN stays immutable, each retry restores from it. Cost: one `cp -r` (~10MB). Benefit: a bug-resistant resume loop.
- **The killed journal is the args source-of-truth, and it's only safe to read BEFORE a bad resume** — capture `.args` at pause time (Step 2.4) AND make GOLDEN at Step 2.5. Once a no-args / bad-args resume has overwritten the journal, `.args` is gone unless GOLDEN exists.

## Anthropic metric source (`workflow-limit-watch.sh`)

- **Watch is account-aware — it follows the logged-in account, not MAX-across-all** (changed 2026-06-06). The workflow burns whichever account the session is actually on, so the watch resolves the active account each poll via `lib/resolve-account.sh` (two-stage: `$CLAUDE_CONFIG_DIR/.claude.json` → `$HOME/.claude.json`) → `quota-<email,@→_at_>.json`. Two payoffs: (a) no false pause from an *idle* account sitting high; (b) **switch accounts to expedite** — if a run is paused at 88% on account A, `/login` to a fresh account B (in-session, don't restart) and the reverse-watch reads B's low number and auto-resumes onto B's quota. CC refreshes *all* configured accounts' quota files continuously (verified: idle 同事帳號 file updated 19s ago while owner was active), so the inactive account's number isn't stale. Billing side VERIFIED (2026-06-07): a run paused on owner at 88% was resumed after `/login` to alex — during the resume alex went 0%→43% while owner stayed flat at 89%, so the resumed workflow's in-flight agents bill the NEWLY logged-in account, not the original. So switching accounts genuinely expedites. (The cache prefix still replays free regardless of account.)
- **Account resolution must be two-stage — `$HOME/.claude.json` alone watches the wrong account in every lock session** (2026-08-01, found by the user asking "會不會有 bug"). Symptom: the guard silently protects an account the session isn't burning. Both failure directions fire: the watched account creeping up → false pause of a healthy run; the actually-burning account saturating → **total miss, no pause at all**. Root cause: `cc -max` / `cc -team` (see `~/.zshrc` `_cc_dir`) launch with `CLAUDE_CONFIG_DIR=~/.claude-max|-team`, and only that dir's `.claude.json` reflects the session's real account — `$HOME/.claude.json` stays pinned to the user-global default forever. Live case: a 13-agent workflow ran entirely on 同事帳號(Max) while the armed watch polled owner(Team) at 7d=95%, one trivial tick from a false trip on a run that was actually at 0%. The statusline was right the whole time (`usage-color.sh:107-111` has had the two-stage read since it was written, and orders the session's account first — that's what "Max: 0% … Team: 84%" was telling us); three consumers had drifted from it: `workflow-limit-watch.sh:67`, `session-limit-watch.sh:28`, `session-limit-nudge.sh:18`. Fix: extracted `~/.claude/scripts/lib/resolve-account.sh` (`cc_resolve_account_email` / `cc_resolve_quota_file`) and pointed all three at it; regression fixtures in `resolve-account.test.sh` (9 cases: lock-session hit, no-CONFIG_DIR fallback, main-bug non-recurrence, plus missing dir / malformed json / absent key / null email / empty-string var boundaries) — 9/9 green. Verified background processes DO inherit `CLAUDE_CONFIG_DIR`, so the watch sees it. Positive control: forced-threshold trip printed `5h=1% (active)` = alex's number, not owner's 0%. **Smoke-testing the trip path is non-negotiable** — the first edit of the nudge hook left a dangling `$email` reference that only blew up *past* the threshold check, i.e. exclusively in the one moment the hook exists for; the silent-path test passed clean and hid it.
- **threshold = 90（2026-07-12 trial 結案 promote）** — 原值 85 是 TaskStop lag（extra agents finish）+ cache ~60-90s refresh lag 的安全 buffer。3 週 trial（2026-06-21 起）實測：1 次乾淨觸發（trip 於 90%、in-flight agents 推到峰值 99%、未撞 100% / 無 hard rate-limit）→ 保留 90。⚠️ overshoot 實測上限 99% = 10% buffer 幾乎吃滿，比 deep-research 更重的 fan-out 場景（同時 in-flight 的重 agent 更多）考慮臨時降回 85。結案紀錄在 `~/Desktop/projects/.claude/trials/archived.md`。
- **7d weekly quota is a distinct saturation vector — 6th arg `SEVEN_DAY_THRESHOLD`** (added 2026-06-28 via F24 Phase 1 mid-run live incident). The original watcher only tracked 5h rolling; a long-running deep-research burned owner 7d from 93% → 99% in ~15min while 5h stayed under 90% — no trip fired, and the workflow would have blown the weekly hard limit if not manually caught. The script accepts an optional 6th arg with direction-aware semantics: **DIRECTION=above** (pause guard) = OR-condition (5h≥THRESHOLD OR 7d≥SEVEN_DAY_THRESHOLD, whichever crosses first); **DIRECTION=below** (resume guard) = AND-condition (5h≤THRESHOLD AND 7d≤SEVEN_DAY_THRESHOLD, both must clear). The below-direction AND-condition is load-bearing: a pure 5h-below reverse-watch would fire on the paused account's 5h rolling recovery even when 7d is still saturated, resuming into a workflow that hard-limits on 7d. Both conditions fired end-to-end in the F24 test: above tripped on real 7d=99%, below correctly held owner blocked until cross-day rolling slid 7d to 0%, then resumed. Validated again 2026-06-28: a single combined watcher fired on a real 7d=99% owner hit mid-workflow, the message correctly labeled `7d=99%`, and the pause captured the run cleanly.
- **5h window is rolling** — wait for the oldest usage to slide out, not a fixed reset; watch the `resets_at`. (2026-06-06: a window at 88%→94% dropped to 0% right at its `resets_at`, so a pause→auto-resume cost only ~3 min downtime.)
- **False-trip guard on transient read failure** (2026-07-12) — `read_active_metric` can fail transiently (claude.json mid-write / quota file mid-refresh); an immediate max-fallback then reads the OTHER account and mis-trips in a dual-account setup (real case 2026-07-11: active alex 13%, fallback read owner 100% → false pause). The script only falls back after 3 consecutive failures.

## GLM metric source（已退役；以下只保留歷史）

> **2026-09-02 退役**：GLM producer 與 cache 路徑已移除，`glm-quota-watch.sh` 現為 exit-3 tombstone；以下內容不得再用來啟動 `/workflow-monitor`。

- **歷史：Cache was pushed by a chrome extension, not by CC itself** — `~/.claude/cache/vendor-glm-*.json` is written by the cc-quota-fetcher native messaging host (separate from CC's anthropic quota cache). If chrome is closed / the extension is disabled / the receiver runtime 副本 (`~/.claude/scripts/cc-quota-fetcher-host/quota-receiver.py`) is not deployed, the cache freezes. `glm-quota-watch.sh` self-aborts when mtime > 15 min (`STALE_ABORT_MIN`) and warns past 5 min (`STALE_WARN_MIN`). See `[[reference_z_ai_glm_widget_integration_2026_06_19]]` for receiver runtime-deploy parity 踩坑.
- **5h vs weekly limit selection is by `(type, unit, number)` tuple**, with a fallback by `nextResetTime` window. Z.ai changing unit 編號 doesn't silently break the watch — but you'll see weekly read as 0 if neither the tuple nor the fallback window matches. Run `glm-quota-watch.sh --probe-once` if the numbers look wrong.
- **Lite/Pro/Max tier is not hard-coded** — `data.level` carries it, but the script only uses percentages, so a tier swap is transparent.
- **Single-key vendor** — z.ai has one ZAI_API_KEY and the cache is one `vendor-glm-<profile_id>.json`. No multi-account glob like the anthropic `quota-*.json` case.
- **Peak window inclusive boundary** — 13:55:00 起算、18:05:59 截止, done via HH:MM string compare (zero-padded monotonic). Z.ai's actual 14:00/18:00 倍率 switch atomicity is unverified — the 5-min buffer is a guess; if peak entry burns hotter than expected, narrow it.
- **TZ hard-coded Asia/Shanghai** — never inherits local TZ, so the user can travel across timezones without the watch misfiring. Tests inject `NOW_CN`.
- **Weekly is BOTH a pause trigger AND a resume cap** — pause fires at weekly ≥ 90% (`WEEKLY_PAUSE_CEIL`, early guard) and resume is blocked at weekly ≥ 95% (`WEEKLY_CEIL`). Why both: heavy workflows (daily-topic 等) burn weekly faster than 5h — 2026-07-10 實證 weekly 80%→97%→1310 在十分鐘內、5h 還沒到 85% weekly 已爆 1310，5h-only pause trigger 來不及擋、加 weekly≥90 early pause 在 weekly 撞牆前先停。
- **Pause uses OR / resume uses AND** — pause 任一條成立 fire（5h≥85 OR weekly≥90 OR peak）、resume 三條都成立 fire（5h≤60 AND weekly<95 AND off-peak）. Asymmetric on purpose (hysteresis): 任一維度吃緊就 pause、但 resume 要求所有維度都回穩.
- **Trial-tunable thresholds** — 85/60/95 + weekly-pause-90 are 試水溫 values。2026-07-03 第一輪 review：watch 0 真實觸發（機制未受考驗非壞掉）。**2026-07-10 第一次真實觸發 + 暴露 gap**：daily-topic 第一輪 weekly 燒太快（80%→1310 十分鐘內）、5h-only pause（85/60）來不及擋、watch 偵測到時 workflow 已撞 weekly 1310 → 同日加 WEEKLY_PAUSE_CEIL=90 early pause trigger。85/60/peak-buffer/weekly-pause-90 全部待累積更多真實觸發再校準。Trial entry 在 `~/Desktop/projects/.claude/trials/active.md`（entry 名 `glm-workflow-monitor`，2026-09-02 fork 併回 `/workflow-monitor` 後 trial 標的不變、只是入口改名）。

## Merge history (2026-09-02)

`/glm-workflow-monitor` and `/relay-workflow-monitor` were separate command files
from 2026-06-22 / 2026-06-20 until 2026-09-02. They forked rather than shared:
only ~114 and ~113 lines of the canonical file appeared verbatim in them, and the
2026-08-01 `watchTaskId` + TaskStop-first fix never propagated — `grep -c
watchTaskId` measured **18 / 0 / 0** and `grep -c TaskStop` **18 / 4 / 4**, so
both forks were still stopping watches through the path this file documents as
known-broken. The merge kept `/workflow-monitor` as the single command, moved the
per-vendor metric table into `~/.claude/scripts/workflow-monitor-vendor.sh`, and
unified the state-file namespace to `workflow-monitor-state-<sid>.json` (the three
separate namespaces existed only so three commands could coexist). **Lesson for
the next vendor**: add a `case` arm to the resolver plus a threshold assertion to
`workflow-monitor-vendor.test.sh` — do not fork the command file. A forked
command file has no mechanism that notices when the original gets fixed.
