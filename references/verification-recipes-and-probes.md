# 驗證配方與安全假設

這兩個分支沿用現有驗證、權限與證據格式，不增加審查輪、固定派工或全站掃描；全 repo 掃描只在使用者同意跑 `/deep-check` 時發生（見「深度健檢完整版」）。

## 驗證配方維護

只處理本次新增、修改或重放的功能；沒有可重用驗證配方的任務不建立空索引。

1. 在既有頁面文件、trajectory 或 Verification Log 補齊或更正必要指針：受影響入口、角色／資料／環境前置、fixture／測試命令、可觀察結果與本次證據。已有正本就引用，不複製規格、不另建 feature map。
2. 對照本次受影響的入口與配方。共用同一行為的其他入口未受影響時保留原狀；未實跑的入口標未驗證，不能用鄰近入口的成功代替。只有環境異常或配方改動時，才重查實例身分與必要前置；沿用既有啟動工具，不為此另造 doctor。
3. 如果本次驗收依賴新增、改動或有具體疑點的自訂比較器，就在判 PASS 前用隔離副本改錯一個應受檢的值，沿同一比較入口、遮蔽與容差設定，確認有實際比較且回報差異。只改測試副本，不改產品、原始預期或批准設定；沒比較、錯值全被遮掉或仍判 PASS 時，這條驗證未成立。有效同題證據可沿用；此檢查只證明該錯值抓得到，不擴成每票 mutation 或新 gate。完成後把結果留在原配方紀錄，再接清理。
4. 清理只移除本次建立的 runtime／資料，不移除證據。若證據位於會清掉的路徑，清理前移到既有持久證據位置並更新指針，清理後實際確認仍可讀。配方無變化、證據仍有效時不重跑；沒有新增配方時不多寫一份交付物。
5. 無既有配方之按需初始化與兩層維護：當本票驗收需要實機操作（CLI、TUI、背景服務或 UI），而目標 repo 尚無任何可重用驗收配方時，於開工唯一一輪提問順便詢問是否初始化第一套最小配方（啟動、就緒探測、模擬操作、取證、清理）；日常收尾預設走簡單版（僅按第 1–4 點維護本次受影響的局部配方，不另建 feature map），只有大改版或使用者明確點名時才走完整版（盤點專案入口與驗收覆蓋缺口、清理已刪功能的過期驗收步驟）。

## 安全假設 probe

只在已有改動或 finding 的安全結論依賴尚未證明的行為事實時使用。純靜態問題、有效證據已覆蓋的事實、沒有這種依賴的改動，都沿原流程，不為此追加檢查。

1. 在原 finding／Verification Log 寫出承重事實及最小反例。沿用已有的 root／first_nail：指定輸入、動作、PASS／FAIL 訊號與執行上限，不另開一輪設計審查。
2. 先對目標 revision、釘定依賴版本與呼叫路徑。若有已授權、可隔離的最小測試，就執行真實模組／依賴的該路徑，保存命令、輸入、預期與實際結果；不要 mock 掉待證行為。不存在安全測法、要碰正式資料／對外寫入／新憑證或超出授權時，保留「未證明」與阻塞原因，不自行擴權或建新 harness。
3. 把結果附回原核驗項，不加固定 reviewer 或重啟完整 review。反例成立只證明該事實不成立，不自動授權修 code；證據不足不能宣稱安全，也不能單憑不確定就確認有 bug。證據沒變就沿用，不重跑相同探測。

## 效能宣稱核驗

只在任務含效能基準、延遲／吞吐優化或速度宣稱時使用；一般功能修改不觸發。

1. 計時區間內工作真發生且 0 報錯：核對計時區間內的處理筆數、回傳值與輸出確實被消費，排除漏 `await`、快取命中假象、空集合早退或靜默吞錯。
2. 正式環境參數與入口對齊：改前與改後都走日常真實入口（含 wrapper、環境變數、編譯旗標與熱／冷快取狀態一致），不拿裸執行檔預設值比調校後設定。
3. A/B 交錯重跑與瓶頸點名：正式比較時在同一環境將改前／改後交錯跑至少 5 次，回報中位數、全距、資源瓶頸（limiter）以及該段佔端到端等待時間的比例；若使用者只要求單次粗估（ballpark），明標「單次粗估」免跑 5 次。
4. 單變量控制：比較期間凍結量測腳本與測試輸入，一次只改一個變因；若需多輪迭代探尋最佳解，轉入 `/hillclimb` 流程。

## 視覺零漂移基準鎖定

只在「換底層技術／重構但要求畫面維持一模一樣」時使用；允許視覺改動的設計迭代不觸發。

1. 改碼前先在固定視窗尺寸、資料狀態與主題下擷取基準截圖或終端輸出（並將時間戳、隨機值與動畫凍結）。
2. 收尾時以相同條件擷取改後畫面，逐態比對確認零非預期視覺漂移；自訂像素或結構比較器在判 PASS 前沿用上方「驗證配方維護」第 3 點的隔離副本改錯自檢。

## 狀態與併發三版核驗

只在規格或實作具有「具體交錯順序風險與待證不變量」（多步狀態機、跨 session 搶鎖、超時與重試交錯）時使用；單純有多個狀態欄位的普通 CRUD 不觸發。同一功能在首次確認驗證方式時（`to-spec` 或首次進入 `implement` Preflight）只問使用者一次要選哪一版（第一版／第二版／第三版／不適用）並記入 Testing Decisions／Verification Log，後續階段直接沿用、不重複詢問。三版由輕到重，第二、三版都先做「掃描」：讀程式碼與規格，列出明寫與藏在旗標、欄位組合裡的狀態、不變量與轉換表，以及每個外部事件與故障點（重試、重送、當機、併發）。

1. 第一版（巡檢）：列出不可違反的不變量（如同一憑證不可雙重消耗、任意狀態皆有終止出口無死結），用有步數上限的小腳本跑過狀態轉移，並沿用「驗證配方維護」第 3 點在隔離副本故意改壞一個轉移條件確認檢查會報紅燈再還原。適合狀態少、規則在規格裡已寫明的改動；成本最低，但只涵蓋規格列出的狀態，不讀程式找藏起來的。
2. 第二版（掃描＋巡檢）：先掃描，再拿掃描清單跑第一版；巡檢要涵蓋清單上每個狀態與故障點，沒涵蓋的寫原因。適合改到含隱含狀態的既有程式、跨模組狀態，或從沒巡檢過的舊程式；成本是第一版再加一次讀碼掃描。只靠實作者自己想到的狀態建模型會漏路徑（例如僅巡檢規格明寫路徑時 0 違規，補上讀碼發現的隱含路徑後才抓出跨步驟資料覆蓋 bug）。
3. 第三版（掃描＋模型窮舉）：先掃描，再把最危險的一兩條流程建成狀態機／TLA+ 模型窮舉交錯路徑，抓出最短反例路徑並轉成 Mermaid 狀態圖呈現，將反例實際回放到真實程式碼核對，並在測試資產旁記錄對應版本註記（不另造同步 gate）。模型優先直接呼叫上線程式的判斷純函式，不另抄一份規則；抄本在程式改了之後照樣綠燈（例如對佇列狀態機直接呼叫真實查詢條件窮舉上千個狀態，抓出輪次重疊把已送出列標成取消的反例）。適合要在規格定案的交錯問題（當機、重交、輪次重疊）；成本最高，模型之後要跟著程式維護。
4. 三版找到的問題都要四項都有才寫成「確認」；缺任一項寫「可能，待核對」或「規格未定義、待決定」：
   - 逐字引用被違反的規格句（`檔案:行號`），並附「規格裡有沒有句子說這是刻意的」反查結果；規格已明寫接受的風險標「已知、已接受」。
   - 重現測試照規格寫預期行為、現在是紅燈，另附正常情況的對照組（綠燈）。
   - 測試的起始資料標出正式程式哪一行會寫出它；不把被查的元件或決定結果的查詢換成假的。
   - 由不是寫報告的人對照規格抽查：`implement` 內交給收尾的獨立核驗，單獨掃描由 main 抽查。
   測試綠燈不等於問題成立：模型自寫重現測試時，常因手捏正式程式寫不出的起始資料、把被查的查詢換成假的，或誤將規格既有設計當成缺陷而產生假陽性。
5. 範圍與執行者：
   - `implement` 內選第二、三版時，由實作 agent 自己掃描，範圍限本票改到的檔案與它們直接呼叫或被呼叫的程式；受委派的 worker 不再往下派人。
   - 單獨掃描（`/deep-check` 的狀態與併發項，或使用者說「掃 X 的狀態機」）預設第二版，只產報告不修 code；找到要在規格定案的交錯流程時，在報告的待拍板建議第三版。如果 main 有 Herdr 身分，就照 agent-dispatch Step 0 取得當次派工同意後派 worker 掃；沒有同意或沒有身分時由 main 自己掃，報告寫明掃描者模型。如果要派掃描 worker，就在提出派工同意前讀 `~/.claude/references/state-machine-scan-brief-template.md`，配方與 brief 都照它。
6. 宣稱邊界：回報結果限定為「在指定模型、假設與步數界限內成立」，明確區分完整窮舉與達上限截斷，不把模型通過直接宣稱為實作絕對無死結；掃描的「沒找到」只代表讀過的範圍內沒找到。

## 程式碼歷史動機追查

只在使用者詢問「這段 code 為什麼寫成這樣」，或準備移除「目的不明、但仍可能承擔契約」的防禦性程式碼（retry、timeout、sleep、特例 guard）時使用；普通功能維護不觸發。

1. 先查局部 Git 證據：用 `git blame -L` 與 `git log -S` 找出引入該段的 commit、PR 編號與票號；commit 已寫明原因且與現況無衝突時直接作答，不預設把所有外部服務查完。
2. 局部證據不足時才沿抓到的 PR／票號／關鍵字擴查人寫的脈絡（個人專案查 `ccsi` 與 `memory`；公司專案查 Bitbucket PR、Jira 票與 Slack）。
3. 回報固定分開兩欄：「當初為何加入」（歷史事故或契約；查無記載就寫未知，不假設每個 guard 背後都有事故）與「目前由誰保證」（該不變量現在是否已移往別層或仍由本行承擔），避免把已過期的歷史原因直接當成現在不能刪的理由。

## 程式碼品質簡單版

只在收尾含程式碼改動時使用，只看本次新增或修改的函式；純文件、設定或測試檔改動不觸發。兩項都不擋 commit，結果併入同一份收尾報告，不另開 review 輪。

1. 複雜又沒測到（CRAP）：CRAP ＝ 複雜度² ×（1 − 覆蓋率）³ ＋ 複雜度；複雜度 ≥ 10 的函式在任何覆蓋率下都過不了 10。JS/TS 若本次全套測試能順帶產出 istanbul JSON 覆蓋率（vitest `--coverage --coverage.reporter=json`、jest `--coverage --coverageReporters=json`）就沿用，不為此另跑；在 repo 外的暫存目錄 `npm i --no-save --prefix <暫存目錄> crap-score@1.2.1`，再跑 `<暫存目錄>/node_modules/.bin/crap --json <暫存目錄>/crap.json -v error <repo>/coverage/coverage-final.json`（直接 `npx` 會找不到它的 TS parser；報告寫在暫存目錄，不進 repo）。其他語言或沒有 JSON 覆蓋率時，跑 `uvx lizard --csv <本次改動的檔>` 取每個函式的複雜度，有覆蓋率報告就照公式算，沒有就標「覆蓋率未知」、只列複雜度 ≥ 10 的函式。本次函式 CRAP > 10 的，每個選一種處理：拆開、補測試，或寫一句不處理的理由；本次只改到一兩行的舊函式可寫「舊債，本次不處理」。
2. 結構重複：對本次新增或改動的每個函式，用 `mcp__semble__find_related`（repo 為目標 repo 根、`file_path` 與該函式起始行、`top_k` 3）找最像的既有程式碼，逐筆判斷結構是否相同；名稱與變數不同仍算重複。判定重複的每一對選一種處理：合併成一份、改用既有那份，或寫一句分開保留的理由。不設相似度數字門檻：Semble 分數量的是語意相近，不是結構相同（實測改名複製品約 0.61、逐字複製約 0.92）。Semble 無法使用時改跑 `npx -y jscpd@5.4.2 --min-tokens 50 --reporters json --output <暫存目錄> <改動的目錄>`，並在報告寫明它只抓得到逐字複製。
3. 收尾報告：兩項各寫查了哪些函式、命中哪些、每個怎麼處理；沒命中寫「本次無命中」。只有本次新增函式 CRAP > 10 或有未合併的結構重複時，才在本次收尾回報的待拍板項加一題「要不要跑 `/deep-check` 做全 repo 深度健檢」；純既有函式標「舊債，本次不處理」或兩項都沒命中就不問，同一次收尾只問一次。

## 深度健檢完整版

`/deep-check` 依 repo 實況從下列完整版挑項，這裡是尚無其他正本的做法；不修程式碼、不 commit、不打正式環境。

1. CRAP 全 repo 熱點：用「程式碼品質簡單版」第 1 點的工具跑全 repo，依 CRAP 由高到低列前 20 個函式（附複雜度、覆蓋率、`檔名:行號`），給「先重構哪裡」排序；不要求修完。
2. 全 repo 結構重複：跑 `npx -y jscpd@5.4.2 --min-tokens 50 --reporters json --output <暫存目錄> <原始碼目錄>` 列逐字或近乎逐字的複製；改名後的複製 jscpd 抓不到，再對 CRAP 熱點前 20 個函式各跑一次 `mcp__semble__find_related` 補查。全 repo 的改名複製目前沒有完整工具，報告寫明這個缺口。
3. 冪等實跑：對會寫入的入口（webhook、排程、會重試的背景工作、migration），在隔離環境用同一輸入跑兩次、或跑到一半中斷後重跑，比對資料前後；不真的扣款、發訊息或寫正式資料。

## 全庫設計與一致性檢查

只在 `/deep-check` 選中本項時執行；它是按需健檢，不接評分、修復 loop 或自動改碼。檢查範圍由本次選定的原始碼與專案契約決定，包含未變更碼；一般 PR 審查的範圍不變。

1. **選範圍與標準**：先用 context 裡的專案慣例及 repo 文件確認模組職責、共同契約與依賴邊界。如果要比較同職責模組，就在取證前讀 `~/.claude/review-standards/project-conventions.md` 與 `~/.claude/review-standards/change-integrity.md` 的「成對的面與跨服務契約」；如果要查依賴方向，就在取證前讀 `~/.claude/review-standards/design-and-maintainability.md`。只用適用條文，不複製標準或把變更專用條款硬套全庫。若派 code-reviewer，就在 prompt 明示本項範圍包含未變更碼，僅本項不套 `finding-discipline` 的 unchanged 排除，其餘搜尋、反證與信心規則照用。完成條件：列出受查目錄、選用標準與下列兩種方法各自跑／跳過的理由。
2. **同職責模組對照**：按已確認的共同職責分組，並列各模組的 helper／guard、錯誤傳播與公開介面；目錄或 import 多數只作找候選的線索。遇到差異，讀差異模組、一個契約相同的正常對照及 caller，確認具體輸入下的後果。不同職責、框架接線、生成碼、刻意遷移或外部契約允許的差異不報錯，也不為統一增加抽象。完成條件：每組留共同契約、差異位置、caller 與「違約／合法差異／未確認」判斷；只有可證的違約進 finding。
3. **依賴取證**：先沿用 repo 已有的依賴圖、lint 或解析器；沒有時可唯讀列出受查模組的 import 邊，不為本項安裝 scanner 或自建常駐工具。對循環群回查實際邊；對跨層 import，逐邊對照專案明示的禁止方向，不自行發明架構規則。公開 API、動態載入、延後 import 與 composition root 需核對；沒有 importer 或只有單一 caller 不直接判死碼或壞抽象。完成條件：每個 finding 附來源邊、契約與影響；解析不到的路徑列缺口，不把靜態圖當完整執行圖。
4. **回報並停止**：把兩種方法的證據與反例併回 deep-check 報告，列實際讀過的範圍、跳過項與未知，不要求固定 finding 數，允許零發現。修哪些仍交使用者決定；不改產品程式碼、不 commit、不因分數或清單未清空持續修。完成條件：每筆 finding 能回到契約、程式位置與後果，未確認項不當成缺陷，然後回 deep-check Step 4 成稿。

## trial 觀察

命中任一分支時，在既有 trajectory／Verification Log／review evidence 留一行它改變了哪個決定與證據位置；沒有增量也如實寫。未命中不加空欄、不另開日誌。trial review 從這些原有產物與 session 工具紀錄分別看兩項，不把合成演練算自然使用。
