# 失敗模式探針表（failure-mode taxonomy）

agent 實作後被 fix commit 補洞的失敗模式，按類別列成可對票文逐條問的探針。來源：2026-09-24 對 acme-dashboard-v2 33 張 implement 票的 68 個 fix、以及 oldco-shop／oldco-api／acme-saas 137 個 fix 的逐條判讀；行為類修正裡 F1＋F2 占一半以上。

**誰在哪一步讀**：
- to-tickets 第 3 節 acceptance-readiness pass：逐票對七類問，命中的寫成驗收項並標 `— Failure: Fn`。
- implement 收尾 Step 3.4 的 code-review：拿七類掃 diff，先對票的驗收清單——對得上標 `Acceptance-miss`（票有列、實作沒做），對不上標 `Failure-miss: Fn`（票沒列）；兩種都寫進 Verification Log，並 append 一行到本檔「案例登記」區。
- pr-review：對已產出的 finding 做同樣的兩種標記，只在 PR 帶 spec／驗收清單時判；沒有的註明「缺驗收依據」，不標記不登記。
- 每日 channel（local-analysis）：讀登記區算近 30 天筆數與門檻，維護本檔檔首的 top-2 提醒行。
- `/trial-review`：候選盤點讀登記區沒有 `[reviewed …]` 尾碼的行，提案只有「改某類問句」與「F7 累積形狀升格新類別」兩種，「不改／證據不足／同案」是合法處置；處理後在該行加 `[reviewed YYYY-MM-DD <處置>]`。
- 回流只追加本檔：新案例、新型、問句修改都落在本檔，不改上面幾個流程檔。

**怎麼用**：每類只在「這票有那個東西」時才問——沒有非同步動作就跳過 F1、沒有第三方就跳過 F3。命中才寫，不命中不留空條目。驗收項要寫成可觀察的「條件 → 期望」，不寫「處理 edge case」。

> 近 30 天最常漏：F5（38）、F2（24）｜更新 2026-10-19

## F1 時序：情境切換與非同步

問句：
- 這票的每個 await／mutation／輪詢在飛的期間，使用者切 scope（場區、公司、分頁、年份）、按上一頁、再點同一列、點另一列、刪同一列，會怎樣？舊情境留下的 state、錯誤紅字、選取、快取會不會殘留或蓋掉新情境？
- 有哪個衍生 state 是從 props 推得出來、卻自己另存了一份？資料換掉時它會不會跟著重算？（例：Bottom N 按下後切到全 null 的 complex，chip 卡死）
- 有沒有「讀回的值就是自己剛寫的」的路徑？回音會不會被當成外部更新去 hydrate？
- 前置條件（apiKey、host、cdnHostName、tree 載完）還沒到時，這個 query／effect 會不會先發出去、並把「已跑過」旗標設成 true 而不再重跑？
- 上游 query 失敗導致下游 query 被 disabled 時，loading 判定會不會永遠停在 pending？
- 批次或長流程開頭取一次的 token／快照，跑到後段會不會過期？
- 非同步動作被殺或程序中斷，紀錄停在進行中、缺完成時間時，下游會把它排除，還是把它自己發出的請求誤當成功／恢復證據？
- 同一狀態有幾個 writer？每個 writer 的 read→compute→write 是否整段在鎖內？較早開始、較晚拿到鎖的舊一輪會不會覆寫新狀態或讓 updated_at 倒退？
- 鎖的取得與過期接手本身是否原子？兩個程序同時判定同一把鎖過期時，會不會兩個都接手？
- 同一資料日或同一輸入重跑、補跑，或資料日往回退（改時區、回溯）時，跨輪狀態從哪一份起算？重跑多次結果是否不變，還是會從自己上一次重跑的結果再疊加？
- 這票有關閉／取消流程時，若先進入關閉狀態、再收到在途回呼或回覆，哪些後續動作仍允許？會不會啟動不再允許的新背景工作或子程序，讓收尾漏掉它？
- 這票會啟動子程序時，終端機 Ctrl-C 的 SIGINT 會送到哪些程序？父子程序同時收到訊號後，子程序應立即停止，還是先完成哪些收尾、最多等多久？實際行為會不會破壞這個約定，或把正常中斷記成錯誤？

驗收項寫法範例：`- [ ] 開啟 A 場區的 dataset 失敗後切到 B 場區，B 的清單上沒有 A 的錯誤紅字 — Failure: F1`

## F2 資料形狀：真資料超出 fixture

問句：
- 後端少回哪一個欄位或 map，或欄位存在但型別不符（字串代替 object、array 代替 dict），會白屏或拋錯？fixture 是不是永遠欄位齊全且型別正確？
- 哪個數字被假設成整數（週齡、隻數、百分比）？後端回浮點、負數、極大值時會怎樣？
- 哪個日期被假設成 UTC？農場時區在 UTC 以東時會早一天嗎？各筆資料的時區快照不一致時代表值怎麼取？
- 哪份清單會被權限（IAM／角色）過濾？非 Root 使用者拿到較短的清單，計數與排名母體會不會算錯或洩漏總數？
- 哪個字串長度無上界（混養品種、農場名、地址）？在固定欄寬下會畫到隔壁或被截斷嗎？文字與按鈕同列時，按鈕會不會擠掉必要資訊？
- 哪個標籤或旗標是「累積型紀錄」卻被當成「互斥的目前狀態」用？（例：訂單 tag 同時留著上傳成功與取消成功）
- 哪個 key 大小寫或命名慣例（camelCase／snake_case）是假設而非查證？
- hook／CLI／API 等外部輸入的頂層與關鍵欄位若缺失、null、list 或錯誤型別，會不會例外後 fail-open／fail-closed 到錯的一側？
- 哪個欄位的字串格式（小數秒位數、有無時區）與執行環境版本是假設而非查證？換直譯器版本時，會不會解析失敗後靜默丟資料？
- 判分／驗證比對證據來源時認的是路徑字串還是同一份資料的身分？受測方在 workspace 自建的檔、或別的 attempt 同名路徑，會不會被當成 fixture 的同一份來源？
- 測試的標準答案或允許清單漏掉另一種合法情況時，會不會把正確結果判錯？
- 這次改了儲存格式、命名或欄位時，既有的舊格式資料（舊紀錄、舊批准、舊 journal）新程式讀得懂嗎？會不會被當成不存在、未審，或因缺欄位被當成相等而放行？
- 這票若用路徑限制可讀寫範圍，檢查的是字面路徑還是實際目的地？遇到 symlink、目標尚不存在或路徑解析失敗時，會不會把尚未確認目的地的路徑判成允許？
- 這票若用引述核對結果判定「有依據／查到」，純標點或從不同位置拼出的碎字，會不會也因字串命中而通過？沒有可核對的實質引文時，結果應標成什麼？

驗收項寫法範例：`- [ ] 後端回傳的 dataset 缺 survivalRates 時，頁面以空 map 渲染而不白屏 — Failure: F2`

## F3 第三方契約雙向

問句：
- **對方給我的**：宿主頁面（商家佈景主題、iframe、App Bridge 事件）的 DOM 結構、按鈕選擇器、事件 payload 形狀、URL 是否帶 locale 前綴，哪些是假設？隱藏的重複按鈕、多語系路徑會怎樣？
- **我給對方的**：送出去的查詢字串、API 參數層級、事件 payload 是否對過對方文件或實測？（例：Shopify 查詢語法 AND／OR 優先序、`variants` 放錯層級、intercept 的 `block` 缺 `errors`）
- 對方元件的 `disabled` 擋得住哪些互動、擋不住哪些（`href` 仍可點）？

驗收項寫法範例：`- [ ] 表單 action 帶 locale 前綴（/en/cart）時仍被認成結帳表單 — Failure: F3`

## F4 外部失敗處理

問句：
- 對方逾時、5xx、403、rate limit 時，我方是重試、放行、擋下還是靜默？失敗的簽章會不會被記成「已成功」導致永不重試？
- 對方回 200 但 body 帶 errors 或 data 為 null，會不會被當成功資料往下傳？
- 讀設定或 log 遇到壞格式、半寫或解析失敗時，會不會誤當空資料或成功？能否明報本輪未查？來源這一輪讀不到時，上一輪仍進行中的事件與其 opened_at／等級／暫停會不會被保留，還是被當成已恢復或重開？
- 對方丟棄了我方已 ack 的寫入，有沒有重送或偵測？
- 失敗有沒有上報？上報的內容看得出原因嗎（Error 序列化成 `{}` 就看不出）？
- 這票若呼叫按用量付費的外部服務，除了時間上限，是否也需要用量／花費上限，現有設定能否守住？失敗或逾時時，已知用量／花費是否仍會記錄；無法取得的部分是否明確標為未知？
- 這票若處理含 API key／token 的設定或資料，解析錯誤及其上報會不會把原文中的憑證片段帶到 log 或畫面？
- 主動作已成功後，後置步驟（寫狀態、寫 log、清理）失敗時，會不會把整體報成失敗、讓呼叫端重送？

驗收項寫法範例：`- [ ] 取旗標的請求超過 5 秒沒回應時走預設值，不卡登入 — Failure: F4`

## F5 多入口與多副本漂移

問句：
- 同一行為有幾個入口（create／paid／updated webhook、單筆／批次、兩個 caller）？這票的改動是否每個入口都接到？
- 同一判定是否在前端與後端、或兩個模組各寫一份？「空字串算不算存在」「哪個欄位代表超商取貨」兩邊一致嗎？
- 局部判定在儲存或使用時，會不會被擴大到未判定的部分？
- 同一指標在不同畫面的定義與單位一致嗎（百分點 vs 小數、簡單平均 vs 加權、內插 vs 缺值回 null）？
- 功能旗標開啟後的每條路徑都接齊了嗎？
- 同一個 hook／事件會在哪些執行環境觸發（互動、headless、subagent、背景）？標記「已送達／已處理」的那個環境真的有人在看嗎？
- 同一項檢查（證據真偽、身分掃描、注入掃描）要涵蓋幾個欄位或來源（頂層與巢狀欄位、prompt、路徑、檔案內容、transcript）？每一個都套到同一條規則了嗎？只驗其中一層時，偽造放在沒驗的那層會不會乾淨通過？

驗收項寫法範例：`- [ ] orders/updated webhook 與 orders/create 一樣會回填發票 attribute — Failure: F5`

## F6 邊界值

問句：
- 空集合、0、1、負數、上限、分頁邊界、排序並列、重複項各會怎樣？
- 取得上限前要處理多少資料？新增量超過每輪容量時，積壓是否可見？
- 查詢結果沒有排序時，「取第一筆」是不是隨機？

## F7 其餘主路徑邏輯

不設探針。正常輸入就錯的算錯、條件反了、key 用錯，靠測試與 review 抓；若同一種反覆出現，升格成新類別。

## 案例登記（回流機制追加區）

每行七欄：`YYYY-MM-DD | <Failure-miss|Acceptance-miss> | Fn | <repo> | <ticket 或 PR> | 條件 → 症狀 | 發現於（implement-review／pr-review）`

- `Acceptance-miss` 的 Fn 可填 `-`；既有登記中的 `—` 統計時視為 `-`，原始列保留。`Failure-miss` 的 Fn 是 F1–F7 之一。
- 處理過的行在行尾加 `[reviewed YYYY-MM-DD <處置>]`，尾碼不算欄。
- 登記區目前 0 行（2026-09-25 定格式時），所以只有這一種格式、沒有舊格式相容分支。首批 149 例的逐條判讀見 2026-09-24 研究副檔（scratchpad，非持久），不在此登記。
